# Global Services

User-level daemons that start on login, managed by
[Pitchfork](https://pitchfork.jdx.dev/).

## Configuration

Services are defined in `~/.config/pitchfork/config.toml`. Each
`[daemons.<name>]` section declares a service in the `global` namespace.

Set [`boot_start = true`](https://pitchfork.jdx.dev/reference/configuration.html#boot-start)
for services that should start automatically on login. See the
[configuration hierarchy](https://pitchfork.jdx.dev/reference/configuration.html#configuration-hierarchy)
for how this user config combines with project `pitchfork.toml` files.

`[settings.general] mise = true` is a
[pitchfork setting](https://pitchfork.jdx.dev/reference/configuration.html#mise):
it runs native pitchfork daemons through `mise x --` so they get mise tools and
env ([mise integration](https://pitchfork.jdx.dev/guides/mise-integration.html)).
Daemons generated by `mise daemons` already run in their project's mise env and
don't need it.

## Shared with Mise Daemons

[`mise daemons`](https://mise.jdx.dev/daemons.html#declare-a-daemon) runs
project dev stacks on pitchfork, one isolated set of daemons per git worktree
(see [Mise Daemons](tools/mise.md#daemons)). To
[start them on demand](https://mise.jdx.dev/daemons.html#register-for-on-demand-startup)
it registers every checkout in this file as a
[`[namespaces.<name>-<hash>]`](https://mise.jdx.dev/daemons.html#namespaces)
entry ([namespace registry](https://pitchfork.jdx.dev/reference/configuration.html#namespace-registry)),
and pitchfork rewrites the whole file in its own serialization on each
registration: comments and `description` keys are dropped, `retry` and `cron`
are normalized.

So chezmoi manages it with a
[modify template](https://www.chezmoi.io/user-guide/manage-different-types-of-file/#manage-part-but-not-all-of-a-file),
`home/dot_config/pitchfork/modify_config.toml`, which renders the daemons and
settings and keeps whatever `[namespaces.*]` entries the file already has.
Write those sections the way pitchfork serializes them, or `chezmoi status`
shows a cosmetic diff after every registration.

Deleted worktrees leave entries behind. Run from a surviving checkout of the
project,
[`mise daemons prune --yes`](https://mise.jdx.dev/daemons.html#pruning-deleted-projects)
(see also [non-interactive cleanup](https://mise.jdx.dev/daemons.html#non-interactive-cleanup))
stops the deleted checkout's daemons, detaches its generated config (the
`config = [...]` key) and deletes `~/.local/state/mise/daemons/<hash>/`, but
leaves its `[namespaces.<name>-<hash>]` entry with only a `dir` line (and an
empty, harmless `<hash>/project.lock` directory).
[`pitchfork clean --prune`](https://pitchfork.jdx.dev/cli/clean.html) drops
`pitchfork list` entries whose directory is gone. Neither, nor
[`pitchfork config remove`](https://pitchfork.jdx.dev/cli/config/remove.html),
removes the leftover namespace entry.

A project's worktrunk `post-remove` hook can run all of this, plus a filter for
the leftover entries, on every `wt remove`; see
[Per-Project Lifecycle Hooks](tools/worktrunk.md#per-project-lifecycle-hooks).
Without it, delete the leftover entries by hand while no daemons run, since a
running supervisor may rewrite the file.

Global `[daemons]` in mise's global config are not a replacement for the user
daemons here: they
[join every project's daemon set](https://mise.jdx.dev/daemons.html#configuration-inheritance),
and `mise daemons` refuses to run outside a project.

## Cron Jobs

Scheduled tasks are regular daemons with a `cron` field. The schedule
uses **6-field** cron syntax:

- second
- minute
- hour
- day-of-month
- month
- day-of-week

The `retrigger` field controls re-execution behaviour when the schedule fires
again:

| Value       | Behaviour                                      |
|-------------|-------------------------------------------------|
| `"finish"`  | Retrigger after the previous run completes (default) |
| `"always"`  | Trigger every time the schedule fires            |
| `"success"` | Only retrigger if the previous run succeeded     |
| `"fail"`    | Only retrigger if the previous run failed        |

Output goes to `pitchfork logs <name>`.

## Bootstrap

The chezmoi script `run_onchange_after_15-enable-pitchfork-boot.sh.tmpl`
enables boot and starts the supervisor on first apply.
